# 070. Идемпотентность

**Статус:** принято.

## Контекст
`POST /enrollments` и `POST /enrollments/waitlist` требуют заголовок `Idempotency-Key`. Повтор с тем же ключом и тем же телом возвращает `201` и тело первого ответа, не создавая вторую запись. Ключ защищает от повторов после потерянного ответа: без него повтор создаст вторую бронь и спишет посещения дважды.

## Решение

**Хранение — таблица Postgres `idempotency_keys`:**

| Колонка | Назначение |
|---|---|
| `user_id`, `operation`, `key` | уникальный индекс — область действия ключа. В `key` — SHA-256 ключа: длина ключа по контракту не ограничена (запись btree-индекса — нет), и ключ не хранится в явном виде |
| `request_hash` | SHA-256 от разобранных полей (`classId`, `seats`), а не от байтов тела: неизвестные поля игнорируются |
| `response_body` | сериализованное тело первого ответа (`jsonb`) |
| `created_at` | для очистки, индекс |

**Область действия:** пользователь + эндпоинт. Один ключ у разных пользователей или на разных ручках не конфликтует.

**Алгоритм (внутри транзакции команды):**
1. `INSERT … ON CONFLICT DO NOTHING` строки ключа в самом начале.
   - Вставилась → выполняем сценарий, сохраняем тело ответа, коммитим.
   - Не вставилась → читаем существующую строку: хеш совпадает — отдаём `201` с сохранённым телом; не совпадает — `409` с `reason: idempotency-key-reused`.
Вставка — сырой SQL: в EF нет `ON CONFLICT`, `Add` + `SaveChanges` на дубликате ломает транзакцию Postgres (`25P02`), а `SELECT` перед `INSERT` — гонка. Просроченный ключ перезаписывается тем же запросом (`DO UPDATE … WHERE created_at < срок`).
2. Одновременный запрос с тем же ключом ждёт на уникальном индексе, пока первый не закончится. Первый закоммитил — второй получает повтор. Первый откатился — второй выполняется как новый.

**Отказ под ключом не сохраняется.** Ключ вставлен в ту же транзакцию и откатывается вместе с ней. Повтор после отказа проверяется заново.

**Срок хранения — 24 часа.** `BackgroundService` раз в час удаляет просроченные ключи порциями. После истечения срока ключ считается новым.

**Порядок в ручке:** `400` (формат, заголовок) → повтор по ключу → проверки состояния. Повтор отдаёт первое тело, даже если состояние с тех пор изменилось.

## Почему 409, а не 422
Черновик IETF `draft-ietf-httpapi-idempotency-key-header-07` рекомендует `422` при другом теле. Но контракт задаёт для этих ручек только `201/400/404/409/429`, а для собственных отказов прямо предписывает «добавьте свою причину в поле `reason`». Поле `reason` есть только у `409`. Вне этого контракта выбрали бы `422`.

## Последствия
- Запись ключа стоит одну вставку в индекс внутри уже открытой транзакции. Конкурируют только запросы с одинаковым ключом.
- Ключ и бронь согласованы: есть оба или нет ничего.
