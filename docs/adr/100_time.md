# 100. Время и даты

**Статус:** принято.

## Контекст
Все моменты времени передаются в UTC в формате ISO 8601. Стандартная привязка ASP.NET возвращает `DateTime` с `Kind=Unspecified` (без смещения) или `Local` (со смещением). Npgsql отвергает оба варианта для `timestamptz`, и запрос падает с `500`. В Postgres точность — микросекунды, в .NET — 100 нс.

## Решение

| Где | Правило |
|---|---|
| Дата и время на входе (`from`/`to` расписания) | свой привязчик: время **обязательно**; без смещения — UTC, со смещением — перевод в UTC; одна дата без времени или мусор — `400` |
| Дата на входе (`from`/`to` аналитики) | строго `yyyy-MM-dd`; значение со временем — `400` |
| Дата и время на выходе | UTC с `Z`, усечение до микросекунд |
| Дата на выходе (`pass.validUntil`, `items[].date`) | `yyyy-MM-dd` (`DateOnly`) |
| Текущее время | только `TimeProvider`; в тестах `FakeTimeProvider` |
| «Сегодня» для срока абонемента | дата текущего момента в UTC; `validUntil` включительно |
| День занятия в аналитике | `(starts_at AT TIME ZONE 'UTC')::date` — явно, не по часовому поясу сессии |

Время, которое пишется в БД (`createdAt`, `cancelledAt`), усекается до микросекунд ещё до сохранения. Тогда ответ из памяти совпадает с ответом из БД и из кэша.

## Почему время в расписании обязательно
Контракт говорит «дата и время». Требование явного времени снимает неоднозначность границы `to` (не включая).
