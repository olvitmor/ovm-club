# 180. Контекст чтения

**Статус:** принято.

## Контекст
Обработчикам запросов не нужны транзакция, отслеживание изменений и запись. Основной `ClubDbContext` отслеживает сущности и разрешает `SaveChanges`. Кроме того, модели записи с навигациями и глобальным фильтром `!IsCancelled` для чтения неудобны: фильтр незаметно прячет брони на отменённые занятия.

## Решение
Отдельный проект `DataReadAccessLayer` со своей моделью, сгенерированной из БД (database-first).

- `ClubReadDbContext.cs` и `Models/` генерируются `dotnet ef dbcontext scaffold` по списку таблиц: `rooms`, `classes`, `enrollments`, `passes`, `waitlist_entries`. Служебные таблицы (`users`, `idempotency_keys`, `__EFMigrationsHistory`) в модель чтения не входят.
- Генерацию запускает `scaffold_db.py`: берёт `ConnectionStrings:Postgres` из `WebApi/appsettings.json`, собирает проект, удаляет прошлую генерацию (scaffold `--force` не удаляет модели исчезнувших таблиц) и генерирует заново. Команда — в README.
- Свои шаблоны `CodeTemplates/EFCore` (штатные шаблоны EF 9 с правками): **модели плоские** — без навигационных свойств и без настройки связей. Связи в запросах выражаются явными `JOIN`. Навигации удалены из шаблонов, а не закомментированы: в проекте принят стиль без комментариев в коде.
- Глобального фильтра отменённых занятий в модели чтения нет: каждый запрос фильтрует явно там, где это нужно (расписание, аналитика).
- `NoTracking` задаётся явно при регистрации (`UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)` в `Program.cs`).
- Ручная часть класса — отдельный partial-файл, который генерация не затирает: `SaveChanges` и `SaveChangesAsync` бросают `InvalidOperationException`.
- Регистрация обычным `AddDbContext<ClubReadDbContext>`. Из-за двух контекстов команда миграций в README получила `--context ClubDbContext`. Это команда разработчика, а не сборки или запуска: задание фиксирует только команды сборки и запуска (строки 91–92 и 601 ЗАДАНИЕ.md).

Зависимости: `WebApi → BusinessLogic → DataReadAccessLayer`. Модели записи `DataAccessLayer` стороне чтения не нужны.

## Последствия
- Контекст чтения используется только в обработчиках запросов. Команды читают через `UnitOfWork` в своей транзакции ([040](040_cqrs.md)), иначе запрос держал бы два подключения одновременно.
- Модель чтения не зависит от модели записи и не тянет её фильтры и навигации.
- **После каждой миграции модель чтения нужно перегенерировать** `scaffold_db.py`. Если забыть, запросы к новым столбцам не скомпилируются, а удалённые столбцы проявятся ошибкой SQL в тестах (`ClubReadDbContextTests.ReadModelMatchesDatabaseSchema` читает каждую таблицу).
- Запись через контекст чтения невозможна на уровне кода. **На уровне БД разделения нет:** оба контекста используют одну строку подключения. Предполагаемый следующий шаг — отдельный пользователь Postgres только с `SELECT` ([NOTES](../../NOTES.md), «За рамками»).

## Отклонённые альтернативы
- **Второй контекст на моделях записи** (`ApplyConfigurationsFromAssembly`): без генерации, но сторона чтения зависит от моделей записи, их навигаций и глобального фильтра.
- **Пользователь только для чтения через `docker-compose`:** задание просит не менять `docker-compose`, init-скрипты Postgres срабатывают только на пустом томе.
