# 030. Слои и размещение логики

**Статус:** принято.

## Контекст
В проекте многослойная архитектура со сценариями транзакций: анемичные сущности, обобщённые репозитории, `UnitOfWork`. DDD не используется. Задание требует отдельных тестов для контроллера, репозиториев и собственных сервисов.

## Решение
**Бизнес-логика организована по шаблону Transaction Script** (Фаулер, «Patterns of Enterprise Application Architecture»): каждый сценарий — одна процедура, которая выполняет запрос от начала до конца. В нашем случае это обработчик команды или запроса ([040](040_cqrs.md)): открыть транзакцию, заблокировать строки, проверить правила, изменить данные, закоммитить. Сущности — только данные, без поведения.

Почему Transaction Script, а не доменная модель:
- проект уже написан в этом стиле: анемичные сущности, обобщённые репозитории, `UnitOfWork`. Смешение двух стилей хуже любого из них;
- сценарии короткие и независимые, скрипт читается сверху вниз как спецификация ручки из задания, и порядок проверок совпадает с порядком причин отказа в контракте;
- транзакции и порядок блокировок ([020](020_locking.md)) видны прямо в сценарии, а не скрыты в агрегате или репозитории.

Против главной слабости шаблона — дублирования логики между скриптами:
- общие проверки вынесены в политики — чистые функции без состояния и БД (`BookingPolicy`);
- общие выборки вынесены в статические хелперы без собственной транзакции (сборка карточки). Скрипты их вызывают, но не вызывают друг друга;
- перевод из очереди сознательно оставлен в обоих сценариях (отмена и уменьшение мест), чтобы порядок блокировок был виден целиком;
- транзакционный каркас остаётся в каждом обработчике ([060](060_transactions.md)).

Новый проект `BusinessLogic`. Зависимости: `WebApi → BusinessLogic → DataAccessLayer → Common` (запись) и `BusinessLogic → DataReadAccessLayer` (чтение, [180](180_read-context.md)).

| Слой | Отвечает за |
|---|---|
| `WebApi` | HTTP: разбор и проверка формата, `Idempotency-Key`, ограничение частоты, перевод `Result` в код ответа и `ProblemDetails`; модели запросов и ответов контракта |
| `BusinessLogic` | обработчики команд и запросов ([040](040_cqrs.md)), транзакции и порядок блокировок, политики |
| `DataAccessLayer` | сущности, конфигурации EF, репозитории с новыми методами, миграции, сиды — сторона записи |
| `DataReadAccessLayer` | контекст чтения и плоские модели, сгенерированные из БД ([180](180_read-context.md)) |

- **Сущности остаются анемичными**, новые (`WaitlistEntry`, `IdempotencyKey`) делаются так же. Смешивать стиль с «богатыми» сущностями не будем.
- **Сервисов на сущность нет.** Доступ к одной сущности — это репозиторий, единица логики — обработчик сценария.
- **Политики** — вспомогательные функции скриптов, без состояния и без БД: возврат посещений, выбор кандидатов из очереди, приоритет причин отказа. Покрываются юнит-тестами.
- **Модели контракта отделены от сущностей.** Ответы закрытые, а в сущностях есть лишние поля (`UserId`, `CancelledAt`).
- В `BusinessLogic` нет ссылки на ASP.NET, поэтому HTTP не может протечь в логику — это гарантирует компилятор.

## Последствия
- Если сценарии начнут разрастаться и делить всё больше правил, следующий шаг — перенести инварианты в сущности (доменная модель). Для текущего объёма это избыточно.
- Три вида тестов соответствуют трём слоям ([160](160_testing.md)).
- Добавляются один `.csproj` и его запись в `FitnessClub.sln`.
