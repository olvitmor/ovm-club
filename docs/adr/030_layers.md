# 030. Слои и размещение логики

**Статус:** принято.

## Контекст
В проекте многослойная архитектура со сценариями транзакций: анемичные сущности, обобщённые репозитории, `UnitOfWork`. DDD не используется. Задание требует отдельных тестов для контроллера, репозиториев и собственных сервисов.

## Решение
Новый проект `BusinessLogic`. Зависимости: `WebApi → BusinessLogic → DataAccessLayer → Common`.

| Слой | Отвечает за |
|---|---|
| `WebApi` | HTTP: разбор и проверка формата, `Idempotency-Key`, ограничение частоты, перевод `Result` в код ответа и `ProblemDetails`; модели запросов и ответов контракта |
| `BusinessLogic` | обработчики команд и запросов ([040](040_cqrs.md)), транзакции и порядок блокировок, политики |
| `DataAccessLayer` | сущности, конфигурации EF, репозитории с новыми методами, миграции, сиды |

- **Сущности остаются анемичными**, новые (`WaitlistEntry`, `IdempotencyKey`) делаются так же. Смешивать стиль с «богатыми» сущностями не будем.
- **Сервисов на сущность нет.** Доступ к одной сущности — это репозиторий, единица логики — обработчик сценария.
- **Политики** — небольшие классы без состояния и без БД: возврат посещений, выбор кандидатов из очереди, приоритет причин отказа. Покрываются юнит-тестами.
- **Модели контракта отделены от сущностей.** Ответы закрытые, а в сущностях есть лишние поля (`UserId`, `CancelledAt`).
- В `BusinessLogic` нет ссылки на ASP.NET, поэтому HTTP не может протечь в логику — это гарантирует компилятор.

## Последствия
- Три вида тестов соответствуют трём слоям ([160](160_testing.md)).
- Добавляются один `.csproj` и его запись в `FitnessClub.sln`.
