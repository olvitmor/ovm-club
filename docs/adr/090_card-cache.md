# 090. Кэш карточки брони

**Статус:** принято.

## Контекст
Задание, раздел 4: «карточку читают часто, и она может отдаваться из кэша. При этом клиент обязан видеть актуальные значения после операций этого API».

В карточке есть `pass.remainingVisits`. Любое списание или возврат посещений устаревает **все** карточки пользователя, а перевод из очереди — карточки другого пользователя.

## Решение
Кэшируется только ответ `GET /enrollments/{id}` целиком, через существующий `ICacheService`. Схема — версия пользователя:

- `card-ver:{userId}` — число. Отсутствие ключа означает версию 0;
- ключ карточки — `card:{userId}:{version}:{enrollmentId}`, TTL 5 минут;
- чтение: `GET` версии → `GET` карточки → при промахе запрос в БД и `SET`;
- `userId` в ключе: чужая бронь никогда не попадёт в кэш текущего пользователя, проверка владельца выполняется до записи в кэш.

**Сброс** — `INCR card-ver:{userId}` после коммита ([060](060_transactions.md)):

| Команда | Чьи версии сбрасываются |
|---|---|
| записаться | инициатор |
| изменить число мест | инициатор и переведённые из очереди |
| отменить бронь | инициатор и переведённые из очереди |
| встать в очередь / уйти из очереди | не сбрасываются: карточки броней не меняются |

## Почему без гонки
Если чтение достало старые данные и записало их в кэш после сброса, запись ляжет под старой версией, и её никто не прочитает.

## Последствия
- Изменения в БД в обход API кэш не видит. Задание этого и не требует, срок ограничен TTL.
- Redis недоступен → читаем из БД, кэш пропускаем.
- Сбой `INCR` после коммита оставит устаревшую карточку до истечения TTL. Пишем ошибку в лог. Риск принят, вероятность низкая.

## Отклонённые альтернативы
- Кэшировать бронь без абонемента: каждое чтение всё равно идёт в БД.
- Не кэшировать: законно («может»), но подготовленный `ICacheService` остаётся без применения.
