# 170. Нагрузочная проверка

**Статус:** принято.

## Цель
Проверить подсчёт мест на лету ([010](010_seat-accounting.md)) и блокировки ([020](020_locking.md)) на объёме «сотни тысяч занятий и броней». Решить, нужен ли переход на счётчик мест.

## Засев — `scripts/load-seed.sql`
Чистый SQL на `generate_series`, без зависимостей. Объёмы — переменные в начале файла:
```sql
\set rooms        50
\set users        20000
\set classes      500000
\set enrollments  2000000
\set waitlist     100000
```
Переопределяются при запуске:
```
docker compose exec -T postgres psql -U club -d club -v classes=1000000 < scripts/load-seed.sql
```
- данные согласованы: занятые места не превышают вместимость, остаток посещений не уходит в минус;
- штатные сиды не меняются: задание запрещает менять состав начальных данных, но разрешает добавлять свои записи для отладки.

## Нагрузка — `scripts/load.js` (k6)
Сценарии:
1. параллельная запись многих пользователей на одно популярное занятие;
2. чтение расписания с переходом по страницам;
3. аналитика за месяц;
4. карточка брони — проверка доли попаданий в кэш.

## Что смотрим
- p95 и p99 времени ответа по ручкам;
- ожидание блокировок (`pg_stat_activity`, `pg_locks`);
- планы запросов (`EXPLAIN ANALYZE`): используются ли индексы;
- инварианты после прогона: места не превышают вместимость, нет отрицательных остатков.

## Критерий пересмотра 010
Подсчёт `SUM(seats)` заметно влияет на время ответа записи или расписания → переходим на счётчик `classes.booked_seats`.
