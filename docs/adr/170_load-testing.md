# 170. Нагрузочная проверка

**Статус:** принято.

## Цель
Проверить подсчёт мест на лету ([010](010_seat-accounting.md)) и блокировки ([020](020_locking.md)) на объёме «сотни тысяч занятий и броней». Решить, нужен ли переход на счётчик мест.

## Засев — `scripts/load-seed.sql`
Чистый SQL на `generate_series`, без зависимостей. Объёмы — переменные со значениями по умолчанию (`rooms` 50, `users` 20000, `classes` 500000, `enrollments` 2000000, `waitlist` 100000, `popular` 20). Значение по умолчанию задаётся через `\if :{?var}`: простой `\set` в файле перезаписал бы `-v` из командной строки. Переопределяются при запуске:
```
docker compose exec -T postgres psql -U club -d club -v classes=1000000 < scripts/load-seed.sql
```
- данные согласованы: занятые места не превышают вместимость, остаток посещений не уходит в минус;
- штатные сиды не меняются: задание запрещает менять состав начальных данных, но разрешает добавлять свои записи для отладки.

## Нагрузка — `scripts/load.js` (k6)
Сценарии:
1. параллельная запись многих пользователей на одно популярное занятие;
2. чтение расписания с переходом по страницам;
3. аналитика за месяц;
4. карточка брони — проверка доли попаданий в кэш.

## Что смотрим
- p95 и p99 времени ответа по ручкам;
- ожидание блокировок (`pg_stat_activity`, `pg_locks`);
- планы запросов (`EXPLAIN ANALYZE`): используются ли индексы;
- инварианты после прогона: места не превышают вместимость, нет отрицательных остатков.

## Критерий пересмотра 010
Подсчёт `SUM(seats)` заметно влияет на время ответа записи или расписания → переходим на счётчик `classes.booked_seats`.

## Прогон
```
docker compose exec -T postgres psql -U club -d club < scripts/load-seed.sql
docker compose exec -T postgres psql -U club -d club -tA < scripts/load-data.sql > /tmp/load/load-data.json
RateLimit__PermitLimit=1000000 ASPNETCORE_URLS=http://localhost:5080 dotnet run -c Release --no-launch-profile --project WebApi
docker run --rm -v "$PWD/scripts:/scripts" -v /tmp/load:/data grafana/k6:0.54.0 run /scripts/load.js
```
Поиск предела — `-e STRESS=1`: чтение расписания и карточек, число VU растёт 0 → 100 → 300 → 500. Предел — ступень, после которой `http_reqs/s` перестаёт расти, а p95 резко растёт. k6 на той же машине, что и приложение, делит с ним процессор: предел получится пределом машины.

Лимит частоты на время прогона выключен: меряем базу, а не лимитер. `POPULAR=n` — номер популярного занятия для повторного прогона (каждое заполняется один раз).

## Результаты (2026-10-13, MacBook, Postgres и Redis в Docker)
Засев: 500 тыс. занятий, 2 млн броней, 100 тыс. записей очереди, 20 тыс. пользователей — 27 с.

k6, 30 с, 92 VU, 144 тыс. запросов (4,3 тыс./с), ошибок 0%:

| Сценарий | p50 | p95 | p99 |
|---|---|---|---|
| расписание, 3 страницы по 100 | 8,7 мс | 19,7 мс | 31,8 мс |
| карточка брони | 5,8 мс | 13,8 мс | 20,5 мс |
| аналитика за 30 дней (41 тыс. занятий) | 252 мс | 442 мс | 528 мс |
| 50 параллельных записей на одно занятие | 832 мс | 1,47 с | 1,52 с |

- **Инварианты после прогона:** переполненных занятий 0, отрицательных остатков 0, популярное занятие заполнено ровно до вместимости (30 из 30 при 100 попытках).
- **Планы:** `SUM(seats)` по занятию — Index Only Scan по `IX_enrollments_class_id_active`, без чтения таблицы. Страница расписания — Index Scan по `(starts_at, id)` со сравнением кортежей, 0,1 мс. Аналитика — Bitmap Index Scan по периоду и подзапрос суммы по индексу, 80 мс в самой БД.
- **Блокировки:** до 47 запросов одновременно ждали блокировку строки популярного занятия. Это ожидаемая сериализация ([020](020_locking.md)): одна транзакция записи держит блокировку ~17 мс (несколько обращений к БД), `SUM` из них — доли миллисекунды.
- **Перевод из очереди при 5000 ожидающих:** отмена брони — 124 мс против ~10 мс при короткой очереди, переведён 1 человек, абонементы всех 5000 кандидатов были заблокированы на время транзакции. Для реальных очередей (десятки человек) приемлемо.

## Вывод по 010
Счётчик мест не нужен: подсчёт на лету читается из индекса за доли миллисекунды. Время записи на популярное занятие определяется блокировкой строки занятия, а она нужна и со счётчиком. 010 остаётся в силе.
