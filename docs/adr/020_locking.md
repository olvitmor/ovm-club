# 020. Защита от гонок: пессимистичные блокировки

**Статус:** принято.

## Контекст
Инварианты задания:
- занятых мест не больше вместимости;
- остаток посещений не уходит в минус;
- посещения за одну бронь списываются один раз.

Они нарушаются при параллельных запросах, если «прочитать → проверить → записать» не сериализовано. При подсчёте мест на лету ([010](010_seat-accounting.md)) менять в строке занятия нечего, поэтому оптимистичная версия строки не помогает.

## Решение
Транзакция уровня Read Committed и явные блокировки `SELECT … FOR UPDATE`. Порядок блокировок всегда один:

1. **строка занятия** — `classes WHERE id = @id FOR UPDATE`;
2. **все нужные абонементы одним запросом по возрастанию id** — `passes WHERE user_id = ANY(@users) ORDER BY id FOR UPDATE`.

Для перевода из очереди ([120](120_waitlist.md)) сначала выбираются кандидаты, затем их абонементы блокируются одним запросом вместе с абонементом инициатора, по возрастанию id. Блокировать абонементы по одному в порядке очереди нельзя: две операции на разных занятиях могут захватить абонементы в разном порядке и получить взаимную блокировку.

Блокирующие выборки сделаны через `FromSql` в методах репозиториев: EF Core не генерирует `FOR UPDATE`.

Выборки занятия в командах используют `IgnoreQueryFilters()`. Глобальный фильтр `!IsCancelled` в `ClassConfiguration` иначе скрыл бы отменённое занятие, и вместо `409 class-cancelled` получился бы `404`.

## Последствия
- Запросы к одному занятию выполняются по очереди, к разным — параллельно.
- Под нагрузкой на одно популярное занятие запросы ждут блокировку. Это допустимо: операция короткая.
- Схема блокировок не меняется, если позже перейти на счётчик мест.

## Отклонённые альтернативы
- **Serializable без явных блокировок:** нужен механизм повторов, под нагрузкой много откатов и непредсказуемые задержки.
- **Оптимистичная версия (`xmin`):** при подсчёте на лету строку занятия пришлось бы искусственно «трогать». По сути это то же самое, только неочевиднее.
