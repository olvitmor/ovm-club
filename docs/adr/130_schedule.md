# 130. Расписание: пагинация по ключу

**Статус:** принято.

## Контекст
`GET /schedule` отдаёт занятия страницами с непрозрачным `continuationToken`. Контракт менять нельзя: других параметров пагинации нет. Занятий сотни тысяч, а в сидах у некоторых занятий одинаковое время начала.

## Решение
Пагинация по ключу `(starts_at, id)`, индекс `classes (starts_at, id)`.

**Токен:** base64url от `{ "s": startsAt, "i": id, "f": hash }`:
- `s`, `i` — последнее отданное занятие;
- `f` — хеш от `from`, `to`, `roomId`. Если токен применён к запросу с другими фильтрами — `400`. `limit` между страницами менять можно;
- подписи нет: подделка токена даёт лишь другую страницу публичного расписания.

**Ход запроса:**
1. Проверка параметров: время обязательно ([100](100_time.md)), `limit` от 1 до 100 (по умолчанию 20), `to > from`, токен разбирается и `f` совпадает. Иначе `400`.
2. Выборка `limit + 1` занятий: `NOT is_cancelled`, `starts_at >= from AND starts_at < to`, фильтр `room_id`, условие `(starts_at, id) > (@s, @i)` при наличии токена, `ORDER BY starts_at, id`.
3. Для занятий страницы одним запросом: `SUM(seats)` активных броней и `SUM(seats)` активных броней текущего пользователя, с группировкой по `class_id`.
4. `freeSeats = max(0, capacity − booked)`, `mySeats` — сумма по всем активным броням пользователя.
5. Пришло `limit + 1` → отдаём `limit`, токен по последней отданной строке. Иначе `continuationToken: null`.

Сравнение кортежей `(starts_at, id) > (…)` Postgres выполняет как переход по индексу: любая страница так же быстра, как первая.

## Отклонённая альтернатива
`OFFSET`: глубокие страницы медленные, а при изменении данных строки пропускаются или дублируются.
