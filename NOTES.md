## Изменения схемы
| Объект | Изменение |
|---|---|
| `enrollments` | колонка `refunded_visits`; частичный индекс `(class_id) INCLUDE (seats) WHERE status = 'active'` |
| `classes` | индекс `(starts_at, id)` |
| `passes` | индекс `(user_id)` стал уникальным: у клиента ровно один абонемент |
| `waitlist_entries` | новая таблица |
| `idempotency_keys` | новая таблица |

Сиды дополнены значениями `refunded_visits` для отменённых броней. Состав начальных данных не менялся.

## Решения по хранению
- **`Idempotency-Key` хранится как SHA-256** ([070](docs/adr/070_idempotency.md)): длина ключа по контракту не ограничена, а уникальный индекс не принимает длинные значения; заодно ключ не хранится в явном виде.

## Свои причины отказа
| `reason` | Ручки | Когда |
|---|---|---|
| `idempotency-key-reused` | 1, 7 | тот же `Idempotency-Key` с другим телом |
| `waitlist-closed` | 7 | до начала занятия меньше часа |
| `already-promoted` | 8 | запись очереди уже стала бронью |

## Известные ограничения контракта
- **Уменьшение брони меньше чем за 2 часа до начала возвращает посещения**, а отмена в то же время — нет ([110](docs/adr/110_enrollment-rules.md)). Уменьшить бронь с 3 до 1 за 10 минут до начала выгоднее, чем отменить. Реализовано по контракту; предлагаем применять к уменьшению то же правило двух часов, что и к отмене.

## За рамками
- **Запись администратором после начала занятия** (например, клиент опоздал на 5 минут). Это не встраивается в `POST /enrollments`: пользователь берётся из токена, а `class-started` по контракту действует для всех. Нужна отдельная ручка вида `POST /admin/enrollments { userId, classId, seats }` со своим контрактом: списываются ли посещения, действует ли вместимость.
- Перевод из очереди при увеличении вместимости занятия: вместимость меняется вне API.
- **Разделение доступа к БД по пользователям.** Предполагается, что контекст чтения подключается отдельным пользователем Postgres с правом только `SELECT`, а команды — пользователем с правом записи. Сейчас оба контекста используют одну строку подключения, и запись из контекста чтения запрещена только в коде ([180](docs/adr/180_read-context.md)). Отдельный пользователь не заведён: задание просит не менять `docker-compose` и настройки подключения, а init-скрипты Postgres срабатывают только на пустом томе.
- **Отдельная строка подключения для чтения.** Следует добавить в конфигурацию `ConnectionStrings:PostgresRead` и регистрировать `ClubReadDbContext` с ней, а `ClubDbContext` оставить на `ConnectionStrings:Postgres`. Это позволит подключать чтение пользователем только с `SELECT` или направить его на реплику. Сейчас оба контекста используют `ConnectionStrings:Postgres` ([180](docs/adr/180_read-context.md)).

## Проверить нагрузочным тестированием
- **Перевод из очереди** ([120](docs/adr/120_waitlist.md)): в память читаются все ожидающие с `seats <= free`, и абонементы всех кандидатов блокируются, даже если мест им не хватит. На длинной очереди это лишние чтение и блокировки. Если подтвердится — отбирать кандидатов в SQL с проверкой абонемента и блокировать только выбранных. **Проверено** ([170](docs/adr/170_load-testing.md)): при 5000 ожидающих отмена занимает 124 мс против ~10 мс — для реальных очередей приемлемо, оставлено как есть.
- Подобные места: выборки без ограничения размера под блокировкой занятия.

## Обсудить
- **Проверка абонемента при постановке в очередь.** Сейчас не проверяется ([120](docs/adr/120_waitlist.md)). Человек с пустым или просроченным абонементом встаёт в очередь, но при переводе его пропускают.
